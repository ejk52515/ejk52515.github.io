Azure AD Domain Controller — Enterprise-Pattern Terraform Build

deployed

The problem

Most tutorial DC builds commit the classic anti-patterns: passwords in variables, a public IP on the most sensitive server in the environment, and click-through configuration nobody can reproduce. The goal here was the opposite — a domain controller whose entire security posture is declared in code.

The build

Terraform deploys the full environment: resource group, VNet with separate AD and Bastion subnets, an RBAC-enabled Key Vault, an NSG scoping RDP to a management IP and the VNet only, and a Windows Server 2022 VM with no public IP and a system-assigned managed identity. A Custom Script Extension installs AD DS and promotes a new forest. Admin access flows exclusively through Azure Bastion — browser-based RDP over TLS. Secrets never touch the codebase: they're populated out-of-band via Azure CLI into Key Vault, which the VM reads with its own identity. State lives in a remote, encrypted backend.

What it demonstrates

Infrastructure as code as a security practice — secrets management, identity-based auth, network isolation, and reproducibility in one build, with every deviation from the tutorial path being a deliberate hardening decision.

Stack

TerraformWindows Server 2022Key Vault (RBAC)Managed identityAzure BastionNSG

Key decisions

  • No public IP on the DC — Bastion only
  • System-assigned managed identity
  • Secrets populated out-of-band
  • Remote encrypted TF state

NTFS File Server Lab — AD, Permissions & Group Policy

deployed

The problem

Every Windows organization faces the same core challenge: Finance data readable only by Finance, HR files invisible to Sales, IT with admin everywhere. That's a permissions architecture problem, and it's easy to get subtly wrong.

The build

Terraform stands up a three-VM domain environment — DC01, file server FS01, and a Windows 11 client — with VNet, NSG, and Key Vault, followed by a PowerShell configuration script that builds the domain (lab.local), department security groups, SMB shares, and layered NTFS permissions, enforced alongside Group Policy. The result is a working model of departmental data access control, from share-level down to NTFS ACLs.

What it demonstrates

The unglamorous core of Windows administration done properly — share vs. NTFS permission interaction, group-based access design, and GPO enforcement — deployed reproducibly instead of clicked together.

Stack

Topology

  • DC01 — domain controller
  • FS01 — file server
  • CLIENT01 — Win 11 workstation

Azure RBAC — Control Plane vs. Data Plane

deployed

The problem

NTFS controls who can access files inside a VM. A different question entirely: who can manage the VM itself from Azure — start it, resize it, delete it? Conflating those two layers is one of the most common access-control mistakes in cloud environments.

The build

Building directly on the file server lab via Terraform data sources, this deploys three role assignments — Owner, VM Contributor, and Reader — scoped tightly to a single VM rather than the subscription or resource group. Test users were created in the tenant and validated against each role, including MFA and device-code login flows. The lab reuses the existing remote-state storage account with its own isolated state key, so the two deployments coexist without touching each other's state.

What it demonstrates

Least-privilege scoping in practice, the control-plane/data-plane distinction interviewers love to probe, and multi-deployment Terraform state discipline — plus real troubleshooting, including state-drift cleanup documented in the SOP.

Stack

TerraformAzure RBACEntra IDPowerShell

Key decisions

  • Roles scoped to one VM, not the RG
  • Terraform data sources across labs
  • Isolated state keys, shared backend
  • Per-role validation with test users

Azure Update Manager — Patch Management & Compliance

deployed

The problem

Manual patching doesn't scale and doesn't prove anything: no consistent maintenance windows, no enforcement, no compliance trail. The interesting problem isn't patching one machine — it's building a process where fleet size stops mattering.

The build

A standalone three-VM domain (DC01 plus two member servers, aumlab.local) deployed with modular Terraform, managed by Azure Update Manager for assessment and installation on defined maintenance schedules, with PowerShell handling orchestration and compliance reporting. The patching regime itself is version-controlled: schedules and scope live in code, not in someone's memory.

What it demonstrates

Process design over heroics — the workflow governs three VMs or three hundred identically, which is the actual measure of automation. The modular Terraform structure also shows code organization beyond a single main.tf.

Key decisions

  • Declared maintenance windows
  • Modular Terraform layout
  • Compliance reporting built in
  • Fully standalone environment

Web App Defense — Application Gateway WAF vs. Live Attacks

deployed

The problem

Turning on a WAF is easy. Knowing what it actually catches — and what slips through, and what it blocks that it shouldn't — requires attacking something behind it and reading the logs. Most people never do that part.

The build

Terraform deploys DVWA on a private VM with no public IP, reachable only through an Azure Application Gateway running WAF_v2 with the OWASP Core Rule Set. With the WAF in Detection mode, I ran SQL injection, stored XSS, command injection, and CSRF against it, then analyzed the results in KQL — including CRS anomaly scoring. A real false positive was found and tuned before switching to Prevention mode, where I confirmed which attacks were blocked and which evaded. A custom WAF rule with priority ordering and evasion hardening closed the gap.

What it demonstrates

Defense in depth as a lifecycle, not a checkbox: detect first, tune, then enforce. Plus offensive fluency (running the attacks), defensive fluency (writing custom rules), and log analysis in KQL — the full loop a security engineer actually works.

Splunk SIEM & Log Analysis

deployed

The problem

Windows endpoints generate a constant stream of authentication events, and without a SIEM nobody can search across them, correlate activity, or spot the patterns that indicate an attack — failed logins and lockouts get noticed when a user complains, not when they start.

The build

A Splunk indexer on an Ubuntu VM in Azure receives Windows Event Logs from a domain server via Universal Forwarder. Network exposure is deliberate and minimal: the Splunk web UI and SSH are scoped to my IP only, and the forwarder port (9997) is open to the VNet range exclusively — never the public internet. On top of that pipeline: SPL searches, dashboards, and alerts for failed logins, lockouts, and authentication trends, worked the way a SOC analyst would.

What it demonstrates

The full log pipeline — collection, forwarding, indexing, searching — plus least-exposure network design and SPL skills that transfer directly to KQL and Microsoft Sentinel.

Stack

SplunkSPLUniversal ForwarderUbuntuWindows Event LogsAzure NSG

Key decisions

  • Forwarder port VNet-only
  • Web UI / SSH scoped to my IP
  • Cross-platform: Linux indexer, Windows source

Nessus Vulnerability Scanning — Full Lifecycle

deployed

The problem

Every network contains weaknesses; the job is to discover, prioritize, remediate, and verify them before they're exploited. A scan report that never leads to a verified fix is just documentation of your exposure.

The build

Nessus Essentials deployed against a Windows Server target in the cloud, running the complete enterprise workflow: an unauthenticated baseline scan, then a credentialed scan for depth, analysis and prioritization of findings, hands-on remediation of a real CVE (CVE-2013-3900, the WinVerifyTrust signature validation weakness), and a re-scan to prove closure rather than assume it. Evidence captured and documented at every stage, including the plugin-compilation and configuration troubleshooting hit along the way.

What it demonstrates

The vulnerability management cycle end to end — discover → scan → analyze → prioritize → remediate → verify → document — with the discipline of proving closure by re-scan, which is the step that separates scanning from managing.
